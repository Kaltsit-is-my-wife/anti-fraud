# 小程序性能优化方案

日期：2026-04-11

前置文档：`docs/performance-investigation-2026-04-11.md`

说明：本文件只讨论解决方案，不包含本轮运行代码修改。

## 目标

本轮优化的目标不是“把所有页面都重写”，而是优先解决最影响体感的三类问题：

1. 首页、用户页、文章详情页首次进入等待时间长。
2. 聊天、阅读、切换 tab 后会出现明显拖尾。
3. 同一个页面背后挂了过重的云函数和重复请求。

## 总体判断

当前有明确解决方案，而且不需要一次性大改架构。

比较稳妥的做法是分三层推进：

- 第一层：热路径减负
- 第二层：查询与写入优化
- 第三层：把同步副作用从主链路拆出去

如果只问“有没有解”，答案是有，而且优先级已经比较清晰。

## 推荐方案总览

### 方案 1：把热路径里的集合探测移出去

适用对象：

- `getUserInfo`
- `trackAction`
- `getArticleDetail`
- `login`
- `getUnreadCount`
- `getTopics`

当前问题：

- 这些云函数在高频调用时，还会反复执行 `ensureCollection`
- 部分函数还会顺手做初始化检查

建议做法：

- 统一新增一个“部署初始化脚本”或“初始化云函数”
- 在部署阶段一次性检查并创建缺失集合
- 线上热路径里移除 `ensureCollection`
- 成就初始化也从热路径移出去，改成后台一次性初始化

收益：

- 每次请求都少掉至少一轮无意义数据库访问
- 热函数逻辑更稳定，抖动更小

风险：

- 需要先保证所有环境的集合都已建好
- 部署流程要补一个初始化步骤

优先级：P0

### 方案 2：把 `getUserInfo` 拆成轻接口和重同步

适用对象：

- `cloudfunctions/getUserInfo`
- 用户页
- 文章详情页
- 其他只想读取用户基础信息的页面

当前问题：

- `getUserInfo` 既做“读资料”，又做“同步成就”，还可能写积分和记录
- 这导致任何读取用户信息的地方都被迫走重逻辑

建议做法：

- 保留一个轻接口，例如 `getUserSummary`
  - 只读 `users`
  - 返回用户资料、积分、权限、签到信息、展示成就 ID
- 把成就同步改成独立入口，例如 `syncUserAchievements`
  - 只在少数关键时机触发
  - 比如签到成功后、答题结算后、后台管理同步时
- 用户页默认先走轻接口
- 文章详情页不要再额外调用重版 `getUserInfo`

收益：

- 用户页和详情页首屏会明显变快
- 用户资料读取不再被成就逻辑绑架

风险：

- 需要梳理哪些页面真的依赖成就同步结果
- 需要接受“成就状态不是每次读页面都实时刷新”

优先级：P0

### 方案 3：重写 `trackAction` 的成就判断方式

适用对象：

- `cloudfunctions/trackAction`
- 聊天
- 阅读文章
- 学习统计

当前问题：

- 它会先查用户
- 再查同类成就
- 然后对每个成就逐个查 `user_achievements.count()`
- 之后再做多次写入

这属于典型的 N+1 查询问题。

建议做法：

- 一次查出当前用户已获得的所有成就 ID
- 一次查出当前 action 对应的成就列表
- 在内存里做差集判断，不要逐个 `count()`
- 最后统一写：
  - 新成就记录
  - 用户 achievements 字段
  - points_records

进一步建议：

- 普通聊天/阅读积分与成就发放拆开
- `trackAction` 先只更新计数
- 成就发放可以延后处理，或者按阈值命中时再触发

收益：

- 聊天和阅读后的拖尾会明显缩短
- 数据库往返次数大幅下降

风险：

- 需要更仔细验证成就发放是否重复
- 需要补测试，避免漏发奖励

优先级：P0

### 方案 4：把文章详情改成“先渲染，再记账”

适用对象：

- `cloudfunctions/getArticleDetail`
- `pages/article-detail/article-detail.js`

当前问题：

- 文章详情接口同时做读文章、加浏览量、写阅读记录、调 `trackAction`、查相关文章
- 前端页面打开时又同时加载评论，还会再同步一次用户信息

建议做法：

- `getArticleDetail` 只负责：
  - 读文章详情
  - 读相关文章
- 浏览量、阅读记录、行为统计改成单独的轻量上报接口
- 前端先渲染详情主体
- 页面显示后再异步上报阅读行为
- 评论请求延迟到首屏绘制完成后再发
- 移除详情页里的 `syncUserInfoFromCloud` 二次重同步

收益：

- 详情页首屏速度会直接改善
- 用户先看到内容，再补统计，不会被行为链路卡住

风险：

- 浏览量和阅读统计会变成“最终一致”，不再是强同步
- 如果用户极快退出页面，可能丢掉少量统计

优先级：P0

### 方案 5：精简 `getArticles`

适用对象：

- 首页资讯列表
- 分类切换

当前问题：

- 每次请求都做 `count + list`
- 分类为空时还会进入调试分支，再扫一批数据
- 日志过多

建议做法：

- 删除线上调试分支
- 删除过量 `console.log`
- 如果首页只需要“是否还有更多”，可以考虑：
  - 查询 `pageSize + 1`
  - 用多取 1 条来判断 `hasMore`
  - 某些场景下不再单独做 `count`
- 若确实需要总数，只对少数页面保留 `count`
- 确保 `timestamp`、`category` 有合适索引

收益：

- 首页列表和分类切换更稳
- 后端日志压力减少

风险：

- 如果页面强依赖总数展示，不能简单移除 `count`

优先级：P1

### 方案 6：优化 `getTopics`

适用对象：

- 社区页

当前问题：

- 先把所有已发布话题拉回来
- 再在云函数里排序和截断

建议做法：

- 在数据库查询层完成排序和 limit
- 避免“全量查回 + 内存排序”
- 对 `status`、`sort`、`publishedAt` 相关查询建立索引

收益：

- 数据量增大后依然可控
- 社区页请求成本下降

风险：

- 需要根据微信云开发索引能力调整排序字段组合

优先级：P1

### 方案 7：把 `login` 收敛成真正的轻登录

适用对象：

- 启动阶段
- 用户更新头像昵称

当前问题：

- `login` 除了读/写用户，还会同步 `public_profiles`
- 这样导致登录接口天然变重

建议做法：

- `login` 只做：
  - 获取 openid
  - 查用户
  - 必要时建用户
- `public_profiles` 同步拆出去
  - 头像/昵称改动时单独同步
  - 或在用户资料保存接口中同步

收益：

- 首次启动和冷启动更轻
- 用户资料修改也更清晰

风险：

- 需要明确 `public_profiles` 的一致性策略

优先级：P1

## 推荐实施顺序

### 第一阶段：先把体感救回来

建议先做：

1. 移除热路径 `ensureCollection`
2. 拆分 `getUserInfo`
3. 重写 `trackAction` 成就判断方式
4. 把文章详情改成先读后记账

这四件事做完，体感上应该就会有最明显提升。

### 第二阶段：减少后端冗余查询

建议再做：

1. 精简 `getArticles`
2. 优化 `getTopics`
3. 收敛 `login`

这部分主要改善首页、社区页和启动稳定性。

### 第三阶段：做结构优化

可以考虑：

1. 成就和积分发放改成异步任务
2. 用户聚合字段做定时汇总
3. 阅读/聊天统计与奖励彻底解耦

这一步属于架构层优化，不建议在第一轮就做。

## 预期收益

如果按推荐顺序推进，预期收益大致如下：

- 用户页：首屏明显变快，切换 tab 后重复等待减少
- 文章详情页：打开后更快看到正文，评论和统计不再拖住首屏
- 聊天页：AI 返回后拖尾减少
- 首页：分类切换和资讯列表刷新更稳定
- 社区页：随着话题增多不至于线性变慢

## 风险与取舍

### 取舍 1：强同步改弱同步

一旦把阅读统计、浏览量、成就发放拆出主链路，就意味着：

- 页面更快
- 但统计数据可能是延后到达

这是值得接受的取舍，尤其是资讯、社区、聊天这类非交易场景。

### 取舍 2：接口拆分后维护成本上升

把 `getUserInfo` 拆成轻接口和重同步后：

- 好处是快
- 代价是接口数量更多

但对当前项目而言，这是合理的工程复杂度交换。

### 取舍 3：需要补测试

特别是以下部分必须补验证：

- 成就是否重复发放
- 积分是否漏记或重复
- 阅读统计是否丢失
- 用户资料是否出现不同步

## 建议的落地策略

推荐不要一次性全改。

更稳的推进方式是：

1. 先做 P0，并保留旧逻辑兜底
2. 用开发环境日志对比改造前后耗时
3. 确认成就/积分没有回归
4. 再推进 P1

## 最终建议

如果只选一套最值得做的方案组合，建议是：

- 方案 1：热路径移除集合探测
- 方案 2：拆分 `getUserInfo`
- 方案 3：重写 `trackAction`
- 方案 4：文章详情改成先渲染后记账

这是当前投入产出比最高的一组优化。

如果只做前端缓存而不动后端重函数，只能缓解体感，不能根治“关键动作卡住”的问题。
